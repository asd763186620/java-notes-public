# synchronized底层原理
## 基础
1. synchronized是一个对象锁，采用互斥的方式，同一时间只有一个线程可以获得锁，其他线程进入阻塞状态。等持有锁的线程释放锁，才会争抢锁。
2. synchronized底层是基于monitor实现的，是由c++编写的jvm级别的对象。线程获得锁需要和monitor进行关联。
    - monitor由三部分组成owner、entrylist、waitset
    - owner是关联获得锁的线程，并且只能关联一个也就是获得锁的线程
    - entrylist是owner中已经关联了获得锁的线程，其它等待争夺锁处于阻塞状态的线程关联entrylist
    - waitset关联的是锁执行了wait方法的线程处于waiting状态中的线程

## 进阶
1.  monitor实现的锁是重量级锁，里面设计到了用户态（java代码）和内核态（cpu）的切换、进程的切换，成本较高，性能低
2. jdk1.6引入了两种锁机制：偏向锁和轻量级锁，解决在没有多线程竞争的场景下使用传统锁机制带来的性能开销问题。
3. java对象在堆内存的布局分为三块：对象头、实例数据（成员变量）、对齐填充（如果对象头+成员变量不是8的整数倍，则通对齐填充补齐）
+ 对象头中包含mark word（对象头）、klass word（实例对象的类型）
+ mark word 中包含锁
+ 32位mark word结构

# 什么是轻量级锁
## 概念
在多数情况中，java程序运行时，同步块中的代码是不存在竞争关系的，不同线程交替执行同步代码块中的代码，这种情况下，重量级锁性能开销大，因此java引入了轻量级锁的概念

+ <!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1776671955926-a994fced-d2ae-4d05-a0ac-26f851944fda.png)

## 工作流程
1. 加锁流程
    - 在线程栈中创建一个Lock Record，将其obj字段指向锁对象
    - 通过cas指令将Lock Record 的地址存入在对象头的mark word 中，如果对象处于无锁状态则修改成功，代表该线程过得了轻量级锁
    - 如果当前线程已经持有锁了，则代表本次是锁重入，设置Lock Record第一部分为null，用于重入计数器作用
    - CAS失败则发生了竞争，需要膨胀为重量级锁
2. 解锁流程
    - 遍历线程栈，找到所有obj字段等于当前锁对象的Lock Record
    - 如果Lock Record的Mark Word为null，代表是一次重入，将obj设置为null后continue（等价与ojb=null，给gc进行垃圾回收）
    - 如果Lock Record的Mark Word不为null，则利用CAS指令将对象头的Mark Word恢复成无锁状态，如果失败则膨胀为重量级锁

# 什么是偏向锁

# JMM（Java内存模型）
## 概念
JMM：java memory model java内存模型，定义了共享内存中多线程程序读写操作的行为规范，通过这些规则来规范对内存的读写操作从而保证指令的正确性

## 结构
JMM将内存分为两块

+ 共享区域（主内存）：包含共享变量
+ 线程私有区域（工作内存）：包含主内存中共享变量的副本
+ 线程与线程之间的私有内存是相互隔离的，线程之间的交互通过主内存来完成

# 什么是CAS
## 概念
Compare and swap （比较在交换），体现了一种乐观锁的思想，在无锁情况下，保证线程操作共享数组的原子性

## 流程

### 主内存中有一个共享内存变量int a = 100
### 此时线程A中有一份副本也是int a = 100 线程A 执行a++操作，此时线程内部的结果是a = 101，写回主内存时，先将a = 100 与主内存中的变量数据值对比，如果相同则返回tru将结果a = 101写入主内存
### 此时同样有线程B，也有一份变量副本int a = 100，线程B执行a--操作，此时线程内部的结果是a = 99，写回主内存时，先将a = 100 与主内存变量对比，此时主内存变量为a = 101 与当前线程的副本数据不一致，此时线程B进行自旋重试操作，如果线程B想要执行成功，就需要再次去主内存读取a = 101写到自己的共享变量副本中才可以执行成功
## CAS性能
因为没有加锁，线程不会陷入阻塞，效率高。但是如果竞争激烈，重试频繁，效率会受到影响

CAS底层是调用的Unsafe类中的方法，操作系统提供的，由其他语言实现

# 乐观锁和悲观锁
## 乐观锁
乐观的态度，不怕别的线程来修改共享变量，改了也不影响，自己可以进行重试。CAS就是基于乐观锁的思想

## 悲观锁
悲观的态度，提防其余线程修改共享变量，我直接上锁在修改，修改完在释放锁其余线程才可以修改。synchronized的就是悲观锁

## volatile禁止指令重排序
### 概念
使用volatile修饰的变量，会在读写共享变量时，加入不同的屏障，读操作会阻止其下方代码越过屏障先读，写操作会阻止其上方代码越过屏障先写。

# 什么是AQS
## 概念
+ 抽象队列同步器，java的一种锁机制，作为基础框架使用，有多个实现例如：reentrantlock，semaphore，countdownlatch
+ AQS内部维护了先进先出的双向队列，有head和tail节点，队列中存储排队的线程
+ AQS内部维护了一个state，相当于一个资源，默认0，如果队列中的一个线程修改成功变成1，则当前线程获得了资源，加锁成功，其余线程进入队列排队
+ 在对state状态进行修改时，利用的CAS操作，保证多个线程修改的情况的原子性

## 公平锁和非公平锁
+ 公平锁：当一个新的线程进来时，直接进入AQS维护的队列中的尾节点，进行排队，由头节点的线程去进行CAS将AQS内部的state改为1，获得锁。
+ 非公平锁：当锁释放后，有新线程进来抢占锁，不是直接由队列中的head节点的线程来占有锁，而是与新线程去争抢锁。

## AQS和Synchronized的区别
### 不同：
+ synchronized是java关键字，由C++实现。AQS由Java语言实现
+ synchronized自动释放锁，AQS需手动开启和关闭
+ synchronized锁竞争激烈时是重量级锁，性能差。AQS锁竞争激烈时，提供了多种解决方案

### 相同
都是悲观锁

## <font style="color:#DF2A3F;">CyclicBarrier vs CountDownLatch有什么区别</font><font style="color:#DF2A3F;">⚠️</font>
1. <font style="color:#DF2A3F;">CountDownLatch主线程会等待子线程的计数器减到0为止，一次性不可重复。适合主线程等待多个子任务完成。</font>
2. <font style="color:#DF2A3F;">CyclicBarrier线程之间互相等待，所有线程都到达屏障点时，计数自动重置可重复使用适合多阶段任务，每个阶段所有线程执行完成才进行下一阶段</font>

# Reentrantlock
## 特点
+ 可重入锁
+ 可中断
+ 可以设置超时时间
+ 支持公平锁
+ 支持多个条件变量

## 使用方式

## 实现原理
+ 利用CAS和AQS实现
+ 支持公平锁和非公平锁
    - 公平锁（FairSync）实现方式在创建Reentrantlock对象时，使用有参的构造方法，将公平参数设置为true。
    - 非公平锁（NonfairSync）可以直接使用默认的无参构造方法。
    - 公平锁的效率比非公平锁效率低
    - <!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1777020483869-5de98cdd-01d9-4314-87b3-161c87f5a743.png)

## 执行流程
1. 当有线程抢锁利用cas方式将state状态修改为1，将自身的exclusiveownerthread属性指向当前抢到锁的线程，获取锁成功
2. 如果抢锁修改状态失败，则进入双向队列等候，head属性指向双向链表队列头节点，tail指向尾节点
3. 当自身的exclusiveownerthread属性为null时会唤醒双向队列中等待的线程
4. 是否公平则体现在，新线程进入是进入等待的队列还是与队列头节点争抢锁

## <font style="color:#DF2A3F;">ReentrantLock可重入锁</font>
加锁：当一个线程通过cas修改state为1时，抢占锁成功后，第二次再过来还是当前线程再次加锁的话此时state会进行重入state + 1，多次重入就多次+1

释放锁：每次unlock时state会减1，减到0才会真正的释放锁，其他线程才可以抢锁。

底层的AQS是通过记录当前持有锁的线id来判断是不是同一个线程重入，是的话直接state + 1 不阻塞，如果不是同一线程才会进入队列等待。

state代表的时重入次数不是简单的0 和 1，不是单纯代表有锁和无锁

# 如何保证多线程的执行安全
## 并发编程特征
1. 原子性：一个线程在cpu中的操作是不可暂停的，不可中断，要不不执行要么执行完成
2. 内存可见性：让一个线程对共享变量的修改，对另一个线程可见
3. 有序性：处理器为提高处理效率，可能会对代码进行指令重排，对代码进行优化，不保证程序中的各个语句的执行先后顺序同代码的先后顺序一致，但会保证最终执行结果与代码顺序执行结果一样

# 什么是ThreadLocal
## 概念
ThreadLocal是多线程中对于解决线程安全的一个操作类，它为每个线程都分配了一个独立的线程副本从而解决了变量并发访问冲突的问题，ThreadLocal实现了线程内的资源共享。

每个线程只能设置自己的值不可能设置和获取到其他线程内部的值

## 核心原理
ThreadLocal本质上是一个线程内部存储类，从而让多个线程只操作自己内部的值，从而实现线程隔离。

内部维护了一个ThreadLocalMap，每个线程都有自己的ThreadLocalMap对象，ThreadLocalMap中有一个entry数组用于存放set（）方法存入的数据，同理获取数据也是在entry中获取

## 源码解析
### set方法
1. 首先获取当前线程对象
2. 通过内部的getMap获取线程内部的ThreadLocalMap
3. 查看ThreadLocalMap是否存在数据，如果为空创建一个新的ThreadLocalMap然后将值存入，如果有值则直接更新新值（定位数组下标将值更新）
4. 创建ThreadLocalMap时，内部会初始化一个16位的entry数组，通过hash（ThreadLocal的hashcode值）& 数组entry容量 - 1得到数组中的索引位置然后将值添加到索引位置key就是当前的ThreadLocal对象，value为添加的值，设置size为1

### get、remove方法
1. 首先获取当前线程的线程对象
2. 通过线程对象获取线程内部的ThreadLocalMap值
3. 通过ThreadLocalMap获取entry数组（将threadlcoal作为key然后获取其hashcode，然后通过& 数组的长度-1获取到具体的下标为止，在通过数组获得具体的entry然后判断entry是否为空并且entry的key是否和当前的threadlocal一样如果一样则将entry返回不为空则返回entry.value）

# ThreadLocal内存泄漏问题
## 原理
每个Thread维护了一个ThreadLocalMap，在ThreadLocalMap中的entry对象继承了weakraferendce（弱引用），其中的key是弱引用ThreadLocal实例，value为线程变量的副本

ThreadLocal中的ThreadLocalMap中的key是entry对象是一个弱引用而value的线程副本的值是一个强引用

因此value是不会被gc回收的，而key是弱引用当前内存不够时会将key优先回收此时就发生了内存泄漏

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1777820073371-ae5c1dbf-5b82-4809-a6f9-ec0ce4295cf7.png)

## 解决方案
使用ThreadLocal时，建议主动使用remove方法释放key和value

## <font style="color:#DF2A3F;">为什么将ThreadLocalMap的key设置为弱引用</font>⚠️
如果key设置为强引用的话，如果外部的当外部的threadlocal置空时,由于其内部的map中的key是强引用对象此时gc不会回收当前的threadlocal，最终可能会导致oom。

通过取舍使用threadlocal的remove是最佳解决方案。

## <font style="color:#DF2A3F;">如果ThreadLocal不使用remove时会导致什么</font><font style="color:#DF2A3F;">⚠️</font>
如果不remove的话，线程池中核心线程中的线程的任务执行完毕之后不会销毁，下一个任务来仍然使用此线程会读取到上一个任务中的数据导致<font style="color:#DF2A3F;">数据污染</font>

key是弱引用当内存不够时被gc垃圾回收之后，长期进行会导致<font style="color:#DF2A3F;">内存泄漏（指的是程序申请内存之后，未将不在使用的内存进行释放导致系统资源被白白占有）</font>最终会内存溢出

# <font style="color:#DF2A3F;">什么是happens-before </font>⚠️
## <font style="color:#DF2A3F;">概念</font>
<font style="color:#DF2A3F;">happens-before是jmm（java内存模型）定义的一组规则，保证一个操作的结果对另外一个操作可见</font>

## <font style="color:#DF2A3F;">常见的几条规则</font>
1. <font style="color:#DF2A3F;">程序顺序规则：同一个线程内，前面的代码happens-before后面的代码</font>
2. <font style="color:#DF2A3F;">volatile规则：volatile写happens-before后续的volatile读</font>
3. <font style="color:#DF2A3F;">锁规则：unlock happens-before 后续的lock（解锁后加锁能看到最新值）</font>
4. <font style="color:#DF2A3F;">线程启动规则</font><font style="color:#DF2A3F;">：</font>`<font style="color:#DF2A3F;">thread.start()</font>`<font style="color:#DF2A3F;"> happens-before 线程内的任何操作</font>
5. <font style="color:#DF2A3F;">线程终止规则</font><font style="color:#DF2A3F;">：线程内所有操作 happens-before </font>`<font style="color:#DF2A3F;">thread.join()</font>`<font style="color:#DF2A3F;"> 返回</font>

<font style="color:#DF2A3F;">一句话总结：happens-before就是JMM对程序员的承诺——只要满足这些规则，内存可见性就有保障。</font>
