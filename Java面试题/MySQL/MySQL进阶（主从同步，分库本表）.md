# 主从同步
## 主从同步原理
主库通过binlog二进制日志记录数据库的定义语言ddl语句以及数据库的操作语言dml语句，不包括select和show语句，然后从库读取主库的binlog日志，来执行主库记录的操作。

## 主从同步执行流程 
1. 主库执行sql语句例如建表语句、修改表语句、删除表语句、针对表数据进行增删改语句。
2. 主库的将执行的sql语句记录在二进制文件binlog日志中
3. 从库有独立的iothread线程从主库读取binlog文件
4. 从库将读取到的binlog文件写入自己的中继日志relay log中
5. 从库再有单独的sqlthread线程读取自己日志中的文件然后执行binlog中记录的sql命令执行到从库
6. <!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1779626199996-39193676-ca02-4a2d-8ba8-a5b38434cea6.png)

## 小总结
1. master主库进行事务提交时，将数据变更记录在二进制日志文件binlog中
2. slave从库进行读取主库的binlog文件，写入到从库的中继日志relay log中
3. slave从库重做中继日志中的时间，将主库的变动反映到自己的数据中

# 分库分表
## 分库分表场景
1. 数据量过大超过1000w条或者数据超过20G
2. 业务增长迅速，业务数据逐渐增多
3. 通过索引和主从分离解决不了性能问题
4. IO瓶颈（磁盘IO，网络IO）、CPU瓶颈（聚合查询、连接数太多）

## 概念
单库单标扛不住时，将其查分到多个库、多个表里

分散数据量、分散并发压力

## 拆分策略
1. 垂直拆分
+ 垂直分库
    - 以表为依据，根据业务不同将不同表拆分到不同的库中
    - 按业务对数据进行分级管理、维护、监控、扩展
    - 高并发下，提高磁盘IO和数据量连接数
    - 例如单体架构下的，用户、订单、商品等表，拆分成微服务结构，每个微服务有自己的库，例如用户微服务有自己用户相关的表，订单微服务有自己订单相关的表等
    - <!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1779627734587-272f48d6-50c2-46f2-bd61-f205d2ed1719.png)
+ 垂直分表
    - 以表的字段为依据，根据字段属性不同将字段拆分到不同的表中
    - 将不常用的字段单独创建一张表存放
    - 将text、blob等大字段拆分到附表中
    - 冷热数据分离
    - 减少IO过度争抢，两表互不影响
    - 例如：当前有商品表，表中有名称、价格、分类、简介、详情等字段，可以将简介、详情等数据大的字段拆分到商品详情表中。
    - <!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1779627859420-7505ccf1-a5e8-4fd1-a755-379c73409cfb.png)
2. 水平拆分
+ 水平分库
    - 将一个数据库，拆分到多个库中
    - 根据id节点取模
    - 根据id范围路由，节点1（1-100w）节点2（100w-200w）
    - 解决了单库大数量、高并发的性能瓶颈问题
    - 提高了系统的稳定性和可用性
    - 例如：当前订单微服务数据量过大到了千万，在当前订单微服务所在的服务器中，创建多个订单库，根据id%具体的订单库数量，将其分配到具体的订单库中
    - <!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1779628049422-12d39a90-e262-466f-a9be-d71279d348ed.png)
+ 水平分表
    - 将同一个库中或者分库的表，查分成多个表
    - 优化单一表数据量过大产生的性能问题
    - 避免IO争抢减少锁表几率
    - 例如：当前订单微服务中的订单1库中数据量累计又超过了1000w，不进行分库而是进行在订单1库中，将订单表中的数据进行拆分成多个表，具体数据在通过id%分表数量进行获取具体的表，进行操作。
