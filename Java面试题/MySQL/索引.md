# 什么是索引
## 索引含义
索引（index）是帮助mysql用于高效搜索有序的数据结构，在数据之外数据库系统还单独维护了一个满足查找算法的数据结构（B+树），通过指向数据，可以实现在数据结构上实现高级特征的查找算法，这种数据结构就是索引。

## 索引数据结构
索引底层数据结构是B+树，每个在非叶子节点只存储了具体的指针引用而具体的数据全部存放在叶子节点，因此叶子节点即储存了引用也存储了数据并且叶子节点通过双向链表进行连接便于查询

1. 二叉树（二叉搜索树）
+ 查找时间复杂度为O（longn），最坏情况为O（n）

+ B-Tree，B树是一种多叉路平衡查找树，相对于二叉树，B树每个节点都可以有多个分支
+ 每个节点可存储多个key，并且存储key对应的数据，而每个节点可以有多个子节点

4. B+树（特殊的B树）
+ B+树是在B树为基础的一种优化，使其更适合存储索引结构，InnoDB存储引擎使用的就是此数据结构
+ 非叶子节点只存储key和指针
+ 数据全部存放在叶子节点
+ 非叶子节点会存储所有的key和对应的数据包括非叶子节点上的key，并且通过双向链表连接有序存储
+ 磁盘读写代价比B树更低
+ 查询效率比B树稳定
+ B+更适合扫库和区间查询

## 小总结
1. 索引帮助mysql搞笑的获取数据的数据结构
2. 提高数据检索的效率，减低数据库io成本
3. 通过索引列对数据进行排序，降低数据排序的成本，降低cpu消耗
4. 阶数（每个节点存储key的数量）更多，路径更短
5. 磁盘读写代价比B树低，非叶子节点只存储key和指针，叶子节点存储数据
6. B+树更偏于扫库和区间查询，叶子节点是双向链表

# 索引结构（聚簇索引和非聚簇索引）
## 聚簇索引（聚集索引）含义
将索引与数据放在一起，索引结构的叶子节点保存了行数据，每个表必须有而且仅有一个

**索引选取资格：**

1. 如果表存在主键那么主键就是聚簇索引
2. 如果表没有主键id，并且存在唯一索引的话，那么第一个唯一索引就是聚簇索引
3. 如果表中没有主键和唯一索引，那么InnoDB会自动生成一个rawid作为隐藏的聚簇索引

## 非聚簇索引（二级索引）含义
将数据与索引分开存储，索引结构的叶子节点保存的是对应数据的主键，可以存在多个

1. 聚簇索引数据结构

## 回表查询
通过二级索引找到对应的主键id在通过主键id在聚簇索引中找到对应的行数据，这个过程就是回表。

# 覆盖索引
## 概念
通过索引进行查询数据，返回的列的数据，并且能在索引中将所有数据找到

+ select * from user where id = 1;
+ 例如通过主键id查询所有信息，此时id对应行的数据存储在了主键id对应的叶子节点中此时就是覆盖索引。
+ select id,name from user where name = 'Jack'; 此时name字段设置了普通索引
+ 此时通过二级索引查询到最后的叶子节点中保存了主键id并且需要查询的字段中的name就是节点的key，因此直接获取到了要查询的主键id和name，此时也是覆盖索引
+ select id,name,age from user where name = 'Jack';此时也是只有name是普通索引
+ 此时通过二级索引查到叶子节点上的主键id，此时只有id和name的数据没有需要查询的age的信息，因此需要通过id去聚簇索引中再次查询主键id对应的叶子节点中行数据，获取到age在将id，name，age返回，此时进行了回表操作，就不是覆盖索引了
+ <!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1779467522220-3d7aa1bd-7761-4b66-a878-0d4e5bf21eb5.png)

## 小总结
1. 覆盖索引指的是通过索引直接查询数据，在索引的数据结构的叶子节点能获取到待查询的所有数据。
2. 使用主键id查询时，直接走聚簇索引的数据结构，在叶子节点存储了主键id对应行的所有数据，通过一次索引扫描返回，性能高。
3. 如果通过索引返回的数据没有将全部需要的数据返回，那么就会进行回表操作，因此尽量避免使用select *操作。

# MySQL超大分页处理
在数据量过大时，通过limi进行分页查询，越往后分页效率越低

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1779467895535-90998fb2-fe66-49da-88e3-591610c34e7a.png)

**解决方案：**

1. 通过覆盖索引加上子查询的方式
+ select u1.* from user u1 join (select id from user order by id limit 9000000, 10) u2 on u1.id = u2.id order by u1.id;
2. 通过游标分页查询，在查询时带上where条件，将上一页最后一条数据的id带进查询中
3. select * from user where id > 上一页最后一条数据id order by id limit 10;

# 索引创建原则
## 索引分类
主键索引

1. 唯一索引
2. 复合索引

## 创建原则
1. 针对表数据量大，需要频繁查询的数据表
2. 对于表查询大量使用where、order by、group by涉及使用的字段建立索引
3. 选择区分度高的列作为索引，尽量建议唯一索引，区分度越高，索引使用效率越高
4. 如果是字符串类型的字段，建立索引的话，针对字段特点使用前缀索引
5. 尽量使用联合索引，联合索引多种情况可以是用覆盖索引，节省存储空间，避免回表，提升效率
6. 索引不适合太多，影响数据的增删改效率
7. 如果字段不能为null，将字段直接配置为NOT NULL，优化器能知道那个索引能更有效的作为查询

## 小总结
1. 主键索引是唯一的非空索引，InnoDB中就是存储整张表数据的结构。
2. 唯一索引保证索引列的值不重复，例如手机号、邮箱等，唯一索引可以允许多个null
3. 联合索引用于优化多条件查询，但是必须遵从最左匹配原则，从最左的字段开始使用查询。
+ (name, age, city)
+ 可以命中
+ where name = ?
+ where name = ? and age = ?
+ where name = ? and age = ? and city = ?
+ 不容易命中
+ where age = ?
+ where city = ?
+ where age = ? and city = ?

# 索引失效
## 索引失效条件
1. 不符合最左匹配原则
+ name，status两个联合索引
+ 失效
+ select * from user where status = '1' and name = 'Jack';
2. 使用了范围查询列，列后面的字段不会命中索引
+ name，status，address三个联合索引
+ select * from user where name = 'Jack' and status > 1 and address = '北京';后面的address不会命中索引
3. 对于列使用了运算方法
4. 对于字符串列，如果不加单引号导致优化器出发自动类型转换导致索引失效
5. 如果是字符串列，使用了name like '%五' 查询以五为结尾的名字此时会失效，不失效：name like '王五%'查询以王五为开头的名字此时不会失效

## 小总结
对于联合索引遵循最左匹配原则并且不在sql中使用运算方法，如果联合索引中的字段可能涉及到范围查询，那么将可能涉及的列放在联合索引最后面，对于是字符串的列记住添加单引号和使用%结尾。

# SQL优化场景经验
## 表设计优化
1. 通过阿里巴巴手册设置表结构数据类型（tinyint，int，bigint等）
2. 使用字符串时，对于char定长字符串和varchar可变字符串，根据数据选择合适字符串

## 索引优化（根据索引创建原则和索引失效场景设置）
## SQL语句优化
1. 避免使用select * ，应指定具体需要查询的字段，使用覆盖索引命中数据，避免回表
2. 避免写sql索引失效的语句
3. where查询子句中避免使用表达式
4. 尽量使用union all 代替 union  ，union会多一次过滤效率低
5. 多表查询优先使用inner join ，一定使用left join 或者 right join 一定小表驱动大表，而inner join内连接会对表进行优化，自动小表驱动大表。另外两个连接不会调整顺序

## 主从复制，读写分离
如果数据库的读场景较多，为了避免写操作造成的性能影响，可以采用读写分离架构。
