# 如何保证消息不丢失
## 消息丢失场景
在生产者生产消息到投递到MQ，再由消费者消息整条链路，各个部分都有可能出现消息丢失。

1. 生产者向交换机发送消息丢失
2. 交换机向消息队列发送丢失
3. 队列中消息丢失
4. 消费者消费丢失

## 处理机制
**生产者：**

+ 生产者提供了消息确认机制，避免发送到MQ过程中丢失消息。在消息发送到MQ中会返回一个结果给生产者，用于确认消息是否发送到MQ成功。

![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1780193330423-ff126d79-5bc7-4e33-8ab4-0e32cb452786.png)

**MQ：**

+ MQ持久化，MQ默认内存存储消息，MQ重启或宕机之后内存数据清空导致消息丢失，因此开始持久化确保MQ消息不丢失。
+ 开启交换机持久化

![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1780193699709-79202425-76ed-4d3b-a6b4-a8e25cdee907.png)
+ 开启队列持久化

![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1780193706497-463ed97d-147e-4c51-b931-ac5e6b30de66.png)
+ 开启消息持久化，SpringAMQP中的消息默认是持久化的，可以通过MessageProperties中的DeliveryMode来指定
+ <!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1780193712277-f59d0b43-1011-45f3-9830-ddeefd3173a0.png)

**消费者：**

+ 消费者消息确认机制，消费者处理消息之后向MQ发送ACK回执，MQ收到ACK回执之后删除该消息，SpringAMQP提供了三种确认机制。
+ manual：手动ACK，需要在业务代码执行完毕之后手动调用api发送ack。
+ auto：自动ACK，Spring监听确认代码执行是否存在异常，不存在异常则返回ACK，异常则返回NACK。（默认）
+ none：关闭ACK，MQ假定消费者获取消息之后会成功处理，消息投递之后会立即删除

## 如何处理
**生产者：**

+ 通过回调方法进行重试
+ 记录日志
+ 保存到数据库，利用定时任务进行重新投递，发送成功删除表数据。
+ 重试次数过多进行告警通知后端人工干预

**MQ：**

+ 开启交换机、队列、消息的持久化功能

**消费者：**

+ 利用Spring的retry机制，在消费者出现异常时，进行本地重试，例如设置重试3、5次，如果重试之后仍然失败，则将异常消费的消息发送到异常交换机由人工处理。
+ 异常消息保存入库，定时任务重试

# RabbitMQ重复消费问题
## 场景
1. MQ定时投递
2. 消费侧服务宕机，MQ未接收到确认，进行重试投递

## 解决方案
**MQ：**

+ 通过状态判断，当投递成功时，修改状态

**消费端：**

+ 记录消息ID到redis中，通过set nx ，如果存在了直接返回
+ 消费消息时，先查状态根据状态决定直接返回还是执行业务逻辑
+ 关键的业务表中，使用唯一索引，添加重复直接报错通过catch捕获返回正确
+ 分布式锁解决

# RabbitMQ死信交换机（延迟队列）
## 概念
### TTL
Time-To-Live，队列中的消息指定了ttl，当ttl时间到期时扔未消费则变为死信消息。

+ 消息指定了TTL
+ 消息队列指定了TTL
+ 具体的TTL过期时间以消息或者队列指定的最小TTL为准。
+ <!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1780238259387-b521c24c-174d-4a7a-89e2-3d1755729e7a.png)

### 死信：
1. 消费者消费消息失败，将消息的requeue参数设置为false
2. 消息过期
3. 队列消息堆积，等待最早的消息可能成为死信

### 死信交换机
如果队列配置了dead-letter-exchange属性，执行了一个交换机，队列中的死信消息会进入此交换机，此交换机称为死信交换机

### 死信队列
死信交换机绑定的的队列

### 延迟队列：
死信交换机加上TTL过期时间加上对应的死信队列的消费者实现延迟队列/死信队列。

# RabbitMQ消费堆积如何解决
## 出现原因
当生产者向队列中发送消息，消费者侧消费消息的速度跟不上生产者创建的速度，导致队列消息堆积，直到超出队列容量，导致多余消息可能变为死信被丢弃，此为消息堆积问题

## 解决方案
1. 添加多个消费者
2. 利用线程池，多线程处理消息
3. 扩大队列容积，提高堆积上限，采用惰性队列

## 惰性队列
**概念：**

+ 队列接收消息不存储在内存中，直接存储在磁盘中
+ 消费消息时从磁盘读取到内存使用
+ 可存储百万消息
+ 性能稳定但是基于磁盘，受限于磁盘IO，时效性低

# RabbitMQ高可用
## 集群分类
1. 普通集群/标准集群
2. 镜像集群
3. 仲裁队列

## 普通集群/标准集群
1. 集群中的各个节点，共享交换机、以及除当前节点中的队列外其他集群中节点中的队列的原信息（引用），不存储队列中的数据
2. 当通过集群中的某个节点获取数据时，如果不存在于这个节点，那么会从其对应的节点中将数据发送到当前节点并返回
3. 当某个节点宕机时，会导致队列中的消费丢失
4. <!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1780241768271-cb0c9ab5-95b2-4df0-8096-93a66cbe12c9.png)

## 镜像集群.
1. 基于主从复制思想，从节点同步主节点中的交换机、队列、消息等数据
2. 集群中的创建队列的节点是主节点，集群中的其他节点则会创建对应的镜像队列，此时其他节点为镜像节点
3. 一个队列的主节点可能是另外一个队列的镜像节点
4. 所有操作在主节点完成，然后同步给镜像节点
5. 主节点宕机后，镜像节点会替代成为主节点 
6. 当进行主从同步时，未同步完成出现主节点宕机，此时仍然会丢失部分消息

## 仲裁队列
1. 同镜像集群一样，3.8版本之后出现。都是主从模式支持主从同步
2. 使用简单，没有复杂配置
3. 主从同步基于Raft协议，强一致性
