# Redis为什么快
1. Redis是纯内存操作，CPU可以直接操作内存，对比磁盘来说还需要将磁盘页读取到内存中操作后在经过磁盘IO写回，速度比磁盘快了无数倍。
2. Reids是单线程进行操作的，减少了多线程下的CPU的上下文切换
3. Redis是使用的I/O多路复用，非阻塞IO

# I/O多路复用模型
## 概念
Redis由于是纯内存操作，因此Redis的性能瓶颈在网络IO上而不是执行速度，因此IO多路复用模型主要就实现高效的网络请求。

+ Linux服务器将进程的使用内存情况分为了两部分：用户空间、内核空间
+ 用户空间只能执行受限的命令（Ring3），而且不能直接调用系统的底层资源，必须通过内核接口来访问
+ 内核空间可以执行特权命令（Ring0），调用一切系统资源
+ Linux系统为了提高IO效率，会在用户空间和内核空间都加入缓冲区
    - 写数据时，要把用户缓冲数据拷贝到内核缓冲区，在写入设备
    - 读数据时，要内核读取设备将数据读取到缓冲区，拷贝到用户缓冲区

## 如何实现 
### 阻塞IO
用户向系统请求数据时，当内核准备数据阶段和将缓冲区数据拷贝到用户空间阶段都需要等待。

**阶段一：**

1. 用户空间请求系统
2. 此时内核无数据需要向底层请求数据，此时用户需要阻塞等待，底层数据返回给内核
3. 内核将数据返回到自己的缓冲区就绪

**阶段二：**

1. 内核空间将数据拷贝到用户空间的缓冲区，此时用户请求仍然在阻塞等待
2. 拷贝完成之后，用户在处理数据

### 非阻塞IO
用户向系统请求数据时，在内核无数据时，会进行多次请求重试不会阻塞等待，当内核向系统请求数据就绪，拷贝数据到用户空间时，此时用户仍然需要阻塞等待。

非阻塞io模型中，第一个阶段非阻塞，第二个阶段阻塞，虽然第一阶段是非阻塞但是性能没有得到提高，而且多次重试等待会导致CPU空转，CPU使用率升高

**阶段一：**

1. 用户请求系统数据
2. 此时内核无数据告知用户异常
3. 用户得到异常后再次尝试读取
4. 循环往复的读取
5. 知道内核读取系统数据就绪时，返回成功，结束用户循环等待

**阶段二：**

1. 将内核读取到的数据，拷贝到用户缓冲区
2. 此时用户仍然需要进行等待
3. 拷贝完成之后，用户解除等待，操作数据

### 多路复用IO
利用单线程监控多个sockets连接，在某个socket可读、可写时得到通知，从而避免无效的等待，充分利用CPU。

**阶段一：**

1. 用户进程调用select，同时指定要监听的socket集合
2. 用户内核监听多个socket
3. 任意一个或多个返回数据就绪，则返回readable
4. 此过程中用户进行阻塞

**阶段二：**

1. 用户进程找到就绪的socket
2. 依次调用recvfrom读取数据
3. 进程反复调用recvfrom并等待
4. 内核空间将对应就绪的数据成功拷贝到用户空间，用户进程结束等待
5. 用户进程处理数据

**监听方式：**

+ select
+ poll
+ epoll
    - select和poll只会通知用户进程有就绪的socket，并不会指定具体的socket，需要用户进程自行遍历查找
    - epoll则会在通知用户进程socket就绪时，将具体的就绪的socket写入用户空间

# Redis网络模型
Redis通过IO多路复用来提高网络性能，并且支持各种不同的多路复用实现，并且将这些实现进行封装，提供了统一的高性能事件库。

Redis使用IO多路复用模型结合自身开发的事件处理器，来应对多个socket请求

+ 连接应答器
+ 命令回复处理器：Reids6.0之后为了提高性能，使用了多线程来处理回复事件
+ 命令请求处理器：Redis60.之后为了提高接收网络参数和命令转换时的处理速度，增加命令转换速度，增加了多线程进行处理。但是在命令执行时仍然使用的是单线程。
