# Redis使用的场景
1. 用于缓存商品分类信息、用户登录信息、热点数据相关信息。
2. 并且通过Redisson作为分布式锁解决并发抢单问题
3. 使用redis作为缓存队列，作为限流组件

# 缓存穿透
## 概念
缓存穿透指的是请求后端接口去查询数据库中不存在的数据，数据库无法查到也不会写入缓存，导致每次请求都去数据库查询

## 解决方案
1. 参数合法校验，建立ip黑名单
2. 当从数据库查询为空值时，在redis设置一个较短过期时间的值
+ 简单
+ 但是消耗内存，可能发生数据不一致问题
3. 使用bitmap， 
+ biemap：相当于一个bit位为单位的数组，数组中每个单元只能存储二进制0或1
+ 进行缓存预热的时候，程序启动时，添加缓存时将其添加到bitmap中
+ 通过数据id进行多次hash计算bitmap的位置，将其中的值从0改为1
+ 当查询数据时，将id进行hash计算先去bitmap查看是否为1，是1则去缓存查询数据，如果为0则直接返回

# 缓存击穿
## 概念
当从redis中通过某个key获取数据时，恰巧key过期时间到了，此时如果是并发请求，那么会导致大量请求到数据库，将数据库打垮，此时就是缓存击穿

## 解决方案
根据系统场景分为两种，一种强一致性性能差一种高可用性性能好

1. 热点key永不过期
2. 强一致可以添加互斥锁，例如分布式锁，只允许一个线程去数据库查询数据重建缓存，其余线程等待并间隔重试，直到占有锁的线程重建缓存成功在返回数据。

![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1779708662215-b8c68f46-6ddb-4dd4-a126-39a3a4c387ad.png)
3. 注重用户体验，高可用性，可以使用逻辑过期时间处理，在进行reids添加数据时，除却业务数据，还需添加一个逻辑过期时间，当用户查看时，如果过期时间小于当前时间，那么也是使用互斥锁占有锁之后，新开一个线程去数据库查询数据重建缓存，然后释放锁，当前线程在开辟的新线程执行缓存重建时，直接将旧的数据进行返回，此时如果缓存没有重建完成时，进来的所有请求都是直接放回已经过期的数据，不阻塞抢锁。

# 缓存雪崩
## 概念
同一时间多个缓存key过期或者是redis宕机，此时大量请求到数据库中查询数据，导致数据库压力过大。

## 解决方案
1. 统一设置缓存key设置过期时间时，通过添加1-5分钟的随机值，避免同一时间大量key失效
2. 利用咖啡因添加多级缓存
3. 如果是redis宕机，那么可以通过配置哨兵模式和集群来规避
4. 热点key永不过期
5. 结合业务添加限流策略

# 双写一致性
## 概念
当数据库数据进行修改时，缓存中的数据也应该更改和数据库的数据保持一致。

## 结合业务
根据业务场景选择强一致、最终一致

1. 延迟双删策略，有脏数据的可能
2. 无论先删缓存还是先修改数据库都有数据不一致问题
3. 延迟双删尽量降低脏数据出现
4. 一般来说数据库时主从模式，读写分离需要延时，让从数据库同步主数据库操作，延时不可控
5. 因此延迟双删只能控制一点不能绝对控制

# 持久化
## RDB
### 概念
RDB全称Redis Database Backup file（redis数据备份文件），也叫Redis数据快照。将内存中的所有数据记录到磁盘中，当Redis故障重启之后，从磁盘读取快照进行恢复。

有两种方式执行RDB操作，一种直接使用主进程，一种使用子进程。主进制执行会阻塞命令，子进程不会

子进程fork主进程中的页表技术为copu-on-write：

+ 当主进程执行读操作时，访问共享内存。
+ 当主进程执行写操作时，会从共享的物理内促，拷贝一份数据进行写操作。

### RDB执行原理
basave开始时会fork主进程得到子进程，子进程共享主进程的内存数据，完成fork后读取内存数据并写入RDB文件

### 执行流程
1. 由于linux中无法直接操作物理内存，因此操作系统给与redis进程分配了一块虚拟内存 ，并且会维护虚拟内存和物理内存的映射关系表，称之为页表
2. 当执行basave时，会在进程内部fork一个子进程，将主进程中的页表拷贝一份到子进程中
3. 子进程通过复制的页表，操作自己的虚拟内存，根据页表读取物理内存的数据，然后将数据写入到RDB文件中，并且通过新与旧替换的方式进行保存
4. 当子进程进行读写操作时，主进程也可能进行写操作，因此在frok时采用了copy-on-write技术
5. 当主进程执行读操作时，可以访问共享内存
6. 当主进程进行写操作时，会将物理内存中已经存在数据标记为read only，并且会复制一份需要操作数据的副本，然后将写操作执行在副本中，并且修改完毕之后修改页表的映射关系到被操作的副本中，之后的读也会读取修改后的副本数据。  避免了脏写的问题

## AOF
### 概念
AOF全称Append Only File（追加文件）。开启AOF之后redis会将每一个写命令记录在AOF文件中，也就是说AOF本质上是一个命令日志。

### 执行原理
通过开启AOF配置，将redis每次的写操作，记录在aof中，如果redis出现宕机可以通过执行具体命令进行恢复。

并且由于AOF文件记录的是命令，因此文件较RDB文件（二进制文件）大，而且AOF对一条记录的多条操作都会记录，但是其实只有最后一次是有意义的，因此可以通过bgrewriteaof命令，让AOF进行文件重写功能，用最少的命令达成效果。

Redia会在出发阈值时自动重写AOF文件，阈值可以在redis.conf中配置

+ 一种是较之前的文件增长的百分比触发
+ 一种是设置具体的大小触发

# Redis数据过期策略
## 概念
Redis对某些数据设置了过期时间，当数据过期之后需要将其从内存中进行删除，Redis中有两种过期删除的规则，也就是数据过期策略。

## 过期策略
1. 惰性删除
+ 当一个key到期之后，redis不会立刻删除，而是在下一次使用时，检查是否过期然后再进行删除
+ 优点：对CPU友好，只有在使用key时进行检查，对于用不到的key不用浪费时间检查
+ 缺点：如果key没有被使用过，就会一直留存内存中，如果有大量过期key存在不在使用的情况，就会导致内存永远不会释放，导致内存占用率过高
2. 定时删除
+ redis 会定期从内存中获取一部分的key，进行检查key是否过期，如果过期进行删除
+ 定时删除有两种模式：SLOW、FAST
+ SLOW模式是定时任务，redis默认是1秒执行10次，并且每次不能超过25ms，此每秒执行的操作，也可以在redis.conf中进行配置
+ FAST模式执行频率不固定，但每次间隔不能少于2ms，执行时间不能大于1ms。
+ 定时删除优点：可以通过限制删除操作执行的时长和频率减少对CPU的影响，另外定期删除可以有效的释放过期的key占有的内存
+ 缺点：难以确定删除操作执行的时长和频率。

## 实际选择
Redis通过惰性删除和定期删除结合使用。并且为了性能进行了优化尽量不妨碍redis的执行，减少对CPU的影响。

# Redis数据淘汰策略（缓存过多，内存不够时如何处理）
##  概念
淘汰策略指的是，当存储新的key，内存不足时，redis会根据淘汰规则，将对应的key进行删除，

## 分类
1. noeviciton：内存满时，不允许写入新数据。直接拒绝报错，redis默认策略
2. volatile-ttl：针对设置了过期时间的key的剩余时间长短，优先删除时间短的key
3. allkeys-random：针对全局key，随机删除对应的key
4. volatile-random：针对过期时间key，删除对应随机的过期时间key
5. allkeys-lru针对全局key，通过lru算法，将根据key的访问时间来删除，访问时间距离当前时间最远的进行删除
6. volatile-lru针对过期时间key，通过lru算法决定
7. allkeys-lfu针对全局key，通过lfu算法，lfu算法将记录每个key的访问频率，将访问频率最低的进行删除
8. volatile-lfu针对过期时间key，通过lfu算法决定

## 使用建议
1. 优先使用allkeys-lru策略。充分利用lru算法，将最近访问的数据留在缓存中，如果业务有明显的冷热数据区分建议使用
2. 如果数据访问频率不打，建议使用allkeys-random，随机选择删除
3. 如果有置顶需求，根据volatile-lru策略，设置置顶数据不过期时间，这些数据会一直保留优先删除有过期时间的key
4. 如果业务中有高频访问的数据，可以使用allkeys-lfu、volatile-lfu基于lfu算法记录频率，优先删除使用频率低的key

## 使用场景问题
1. 数据库有1000w数据，如何保证内存中的20w数据是热点数据
+ 通过设置redis的淘汰策略为allkeys-lfu、volatile-lfu，将使用频率低的key进行删除，留下的就是热点数据
2. redis内存用完发生什么
+ 根据redis淘汰策略设置的不同，最后保留的key也不同，如果是默认设置那么会直接报错。
