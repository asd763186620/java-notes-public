# 主从复制
单节点的redis实例，并发有上限，因此如果需要提升redis并发能力，就需要搭建主从节点，实现读写分离

**Replication Id：**简称replid，数据集的标记，id一致则说明是同一数据集，每个master都有唯一的replid，slave从节点会继承master节点的reqid；

**offset：**偏移量，随着记录在repl_baklog中的命令日志记录越来越多，slave完成同步时也会记录当前同步的offset。如果从节点的offset小于主节点的offset，则说明主从不一致需要更新

## 主从全量同步
1. 从节点执行同步命令与主节点建立连接
2. 从节点向主节点发送数据同步请求并且携带自身的同步id和offset偏移量
3. 主节点校验id是否与自己一致，判读是否是第一次同步
4. 不一致时，将自身master的数据版本信息中的id和偏移量发送给从节点
5. 从节点接收到id和偏移量后进行保存版本信息
6. 主节点进行bgsave生成RDB文件，发送给从节点
7. 从节点保存主节点发送的RDB文件，清空本地数据然后执行
8. 如果主节点在生成RDB文件期间，有新的写命令，会记录在缓冲区的日志（repl_baklog）中
9. 将生成RDB期间产生的日志发送给从节点
10. 从节点执行日志文件

## 主从增量同步
1. 从节点重启
2. 从节点发送数据同步请求，将自身的版本信息（replid、offset）发送给主节点
3. 主节点根据replid和offset与自身的数据信息进行对比
4. 主节点发现不是第一次请求则回复从节点continue
5. 不相同，从自身的repl_baklog日志中获取从节点携带的offset之后的数据
6. 主节点将获取到offset后的日志命令发送给从节点
7. 从节点执行命令

# 哨兵模式
## 概念
Redis提供了哨兵模式（sentinel），来监控redis集群，实现redis集群的自动故障恢复

**结构：**

+ 配置多个sentinel实例，最好是奇数个
+ redis的主从集群实例
+ java程序中的redis客户端

**作用：**

+ **监控：**Sentinel会不断地监控集群中主从节点的状态是否工作
    - 哨兵的监控会基于心跳机制进行检测，每隔1s向集群中的每个实例，进行发送ping命令
        * 主观下线：当一台哨兵发现一个节点未按照规定时间响应时，则会认为该实例主观下线
        * 客观下线：如若超过指定数量quorum值的哨兵，都认为该实例主观下线，那么则认为该实例客观下线，quorum值可配置最好超过哨兵数量的一半
        * <!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1779802779739-affbb47e-543b-4475-8433-2d246e229b7a.png)
+ **自动故障恢复：**当master主节点出现故障宕机时，sentinel哨兵会将一个slave从节点提升到主节点，并且当之前的主节点恢复之后直接变为从节点，不影响当前的新的主节点。
+ **通知：**哨兵充当redis客户端的服务发现来源，当集群出现故障转移时，会将最新的信息推送给java程序

## 哨兵选主规则
1. 首先判断主节点与从节点的断开时长，如果超过配置的指定时长，则不会被选为主节点，<font style="color:#DF2A3F;">可配置</font>
2. 判断从节点的slave-priority值，该值越小优先级越高，<font style="color:#DF2A3F;">可配置</font>
3. 如果从节点的slave-priority值一样，那么会根据从节点存储的offset偏移量对比，偏移量越大的则代表与主节点同步的数据更全，则优先级越高
4. 如果上述三点全部一样，则根据slave节点的运行id大小，越小优先级越高

## redis集群（哨兵模式）脑裂
当集群中的主节点，由于网络分区的问题，与集群和哨兵断开了连接，并且哨兵在从节点中选择了一个新的主节点，此时客户端新写的数据仍然在老的主节点中，当网络恢复时，老的主节点恢复到集群中是作为从节点的，因此在老的主节点中在网络问题期间存储的数据就会丢失。此问题就是集群脑裂

**解决方案：**

1. redis配置参数一：min-replicas-to-write 1  表示从节点至少为1个
+ 当客户端向主节点写入数据时，必须保证主节点至少有一个从节点
2. redis配置参数二：min-replicas-max-lag 5 表示数据复制和同步的延迟不能超过5秒

# 分片集群
主从复制和哨兵模式解决了，redis的高并发和高可用问题，但是还有两问题没有解决

1. 海量数据存储
2. 并发写

## 结构
1. 集群中有多个master节点，每个master保存不同的数据，并且每个master可以有不同的从节点
2. 多个master通过各自进行ping心跳检测，每个master相当与一个哨兵，并且存在主观下线和客观下线
3. 客户端可以访问集群任意节点，最终都会被路由到正确的节点中

## 数据读写（路由规则）
**概念：**Redis分片集群引入了哈希槽的概念，Redis集群中有16384个哈希槽，每个key通过CRC16校验后通过取模16384来获取决定防止在那个槽，再根据每个节点负责的哈希槽进行存入。

**执行流程：**

**普通写：set name java**

1. 当已有了分片集群，并且集群中的每个主节点都分配好了管理对应的哈希槽
2. 当进行写操作时
3. 会根据CRC16对存入的value值进行hash
4. 得到的hash值在取模16384
5. 根据取模后的结果去对应的哈希槽位置，确定被那个节点管理，就将key存入那个节点

**带条件写：set {条件} name java 确保带相同条件的key存在同一节点中**

1. 如果带条件了，nameCRC16可以根据条件计算hash值
2. 在根据hash值选择对应的节点
3. 确保带有此条件的命令，将对应的key存入相同的节点中
