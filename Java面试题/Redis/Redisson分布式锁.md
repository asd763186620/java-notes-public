# 分布式锁实现原理
## 实现原理
Redis分布式锁主要依靠与Reids的set nx ex 命令。set nx是：set if not exists（如果不存在则set）。

+ 获取锁：set lock value nx ex 10
+ nx是互斥不存在则添加，ex设置过期时间保证锁需要自动释放
+ 释放锁
+ 通过lua脚本判断是否当前线程持有，是才会删除，保证不删除其他线程的锁

## 加锁流程
1. 判断锁是否存在
2. 判断当前线程是否持有锁
3. 如果不是当前线程直接原地循环重试获取锁，如果设置了过期时间会在过期时间内进行反复重试等待通知，如果过期时间内仍然被其他线程持有锁则直接返回失败结果。
4. 如果是并发场景，不设置过期时间的话只抢占一次，然后直接返回失败
5. 如果仍然是当前线程抢占锁那么内部的hash结构key-value（线程id，重入次数），会将重入次数+1，刷新过期时间，加锁成功
6. 否则加锁失败

1. 根据业务判断
2. 给锁续期

## Redisson分布式锁基于Redis实现
1. 当一个线程进行加锁成功后可以去操作redis并且执行业务逻辑
2. 并且redisson在加锁成功后会单独创建一个线程去监听执行业务的线程
3. 根据设置的锁的过期时间，releaseTime / 3的时间去做续期操作
4. 如果没有设置过期时间，redisson会自动给一个默认的30秒过期时间
5. 根据续期操作，十秒钟检查一次如果业务没有执行完毕
6. 线程还在持有锁那么会将锁重新设置为30秒
7. lock.tryLock(3, 10, TimeUnit.SECONDS);
8. 如果通过上述代码进行加锁，设置了自动过期时间那么此时看门狗机制就会失效
9. 十秒后自动释放锁
10. 因此最推荐的是lock.tryLock(3, TimeUnit.SECONDS);
11. 结合过期时间和看门狗机制进行自动续期处理

## Redisson可重入锁
Redisson利用hash结构存储了，锁的相关信息

key为锁名称value中存储了线程id信息和重入次数

如果是同一线程多次加锁成功，那么value中的重入次数就会加1，同时解锁时同样需要多次释放锁，释放锁之后重入次数-1，最后释放锁

## Redisson分布式锁-主从一致性
### 问题
如果加锁时，主节点宕机，导致从节点未获取到最新数据

那么此时redis哨兵模式会在从节点选取一个新的主节点

此时新的线程进来加锁，新任主节点中没有对应的数据，那么此时还会加锁成功

导致多个线程只有同一把锁，可能出现脏数据

![](https://cdn.nlark.com/yuque/0/2026/png/43313275/1779787953881-cf9955a9-a329-40c2-b94d-99594539f279.png)

### 解决方案
Redisson提供了Redlock红锁机制，不能只在单个实例上创建锁

应该在多个redis实例上创建（实例数量 / 2 + 1），例如如果有三个实例，那么3 / 2 + 1 = 2.5，意思就是需要再2个或以上实例中进行加锁操作。

**缺点：实现复杂、性能差、运维繁琐**

**redi是基于AP思想的，保证高可用**

**如果需要强一致性可以使用CP思想的zookpeer**
